<hypothesis_evidence_guidance>
Derive the repair intent from the complete original Issue operation and its observable result,
not merely the compiler-error site or Scout's smallest example. Keep Issue requirements,
baseline observations, causal interpretations and unverified predictions distinct. A baseline
POC records current behavior; it does not define the fixed behavior or a preservation rule.
Passing old tests proves only their exercised inputs/build route. A printed value with exit 0
does not prove the requested value was asserted. Missing execution is uncertainty, not success.
Do not promote an adjacent API or an exploratory Scout probe into a hard requirement merely
because it fails by a similar mechanism. Keep it as a conditional scope lead unless the Issue
or a necessary shared dependency establishes that it must change.

For each plausible direction, connect the supplied evidence along the public operation,
selection/dispatch or state transition, consuming operation, and affected public/build scope.
Identify the specific missing link instead of filling it with a confident assertion. Do not
mistake failure in a downstream consumer for proof that only that consumer should change.
Retain a coherent Issue-related alternative when its causal premise or shared scope is
uncertain; this is why Repair branches exist. Reject it only for a concrete contradiction of
its complete policy, not because Scout did not execute its variant or inspect a sibling.
Graph paths nominate relationships to verify; source/execution establishes their significance.
No graph or missing edge does not establish absence or prove a local-only repair scope.

Give Repair a concrete locus and complete intended behavior, while leaving implementation
recipes falsifiable. Do not turn an untested literal predicate, mask, helper name or suggested
edit into a hard obligation. Explain the required state/result so Repair can reject a faulty
recipe without changing the branch's intent. Preserve Issue-explicit inputs and constraints
and any source-backed necessary closure across packaged/build-selected representations.
When reviewing a branch, distinguish a refuted public policy from an incomplete proposed
implementation. A missing wrapper, consumer or build representation can be repaired within
the same policy; describe that missing surface instead of declaring the whole direction
impossible. Preserve distinct plausible directions for Repair with the review caveat visible.
Check whether other public operations share the exact affected invariant; include connected
ones as scope or preservation evidence without inventing a new Issue requirement.
When reviewing hypotheses, distinguish unsupported certainty from a refuted policy: uncertain
premises can remain conditional branches. Concrete counterevidence should correct the affected
claim, not silently remove the Issue requirement or all alternatives sharing that public goal.
For a repaired candidate, judge the assigned observable behavior and evidence-backed scope,
not literal fidelity to an unverified edit recipe. A different implementation of the same
assigned policy is not a branch violation. Current final-revision failures are counterevidence
even when older repository regression checks pass; missing checks must not be described as
successful verification.
</hypothesis_evidence_guidance>
